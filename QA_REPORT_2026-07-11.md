# Deep QA Report — aboalazm-os.vercel.app
**Date:** 2026-07-11
**Tester:** Automated QA session (browser-driven, live production)
**Scope:** Full functional pass — every page, every button/CTA, all forms, all links, interactive widgets (gallery, book reader, token playground, anchor-nav), console/network health.

---

## Overall Status: **FAIL** — one Critical, one High confirmed defect

The site is broadly stable (routing, assets, most interactivity, and content all work), but this deeper pass surfaced two defects that a smoke test alone would not catch: a **broken contact-form success state** (the site's primary lead-capture mechanism silently fails to confirm success to the user) and a **reduced-motion accessibility bug** that leaves large portions of content — including primary CTAs and the entire gallery — permanently invisible for any user with "reduce motion" enabled at the OS level. A confirmed non-functional control was also found in the Capabilities token playground.

---

## Critical Bugs

### C-1 — Contact form gives no success feedback after a successful submission
- **Severity:** Critical
- **Location:** `/contact` — form submission
- **Steps to reproduce:**
  1. Go to `/contact`.
  2. Fill Name, Email, "What are we building" (all required fields) with valid data.
  3. Optionally select a budget band.
  4. Click "→ BEGIN THE CONVERSATION".
  5. Observe the button and network tab.
- **Expected Result:** Server accepts the submission and the UI shows a clear success confirmation (e.g., "Message sent" state, a thank-you message, or redirect), and the submit button re-enables or is replaced.
- **Actual Result:** The `POST /contact` request returns **HTTP 200** with body `{"ok":true}` — the server confirms success — but the submit button gets permanently stuck showing **"WORKING…"** and remains `disabled`. Verified this state persists unchanged for 10+ seconds with zero console errors and no further network activity. The form fields remain populated with no acknowledgment.
- **Impact:** This is the site's primary conversion action. A real user has no way to know their inquiry was actually sent — they will reasonably assume the form is broken, potentially abandoning the site, re-submitting duplicate inquiries through the form or via WhatsApp/email instead, or losing trust in the business. Silent success-state failures on lead-capture forms are a direct revenue/lead-loss risk.
- **Suggested Fix:** Ensure the submit handler's `.then()`/success branch actually updates component state after receiving `{"ok":true}` — render a success message and either re-enable the form for a new submission or replace it with a confirmation screen.

## High Priority Bugs

### H-1 — Content is permanently invisible for users with "prefers-reduced-motion: reduce" enabled
- **Severity:** High (Accessibility + functional; borders on Critical since it hides primary CTAs)
- **Location:** Site-wide — confirmed on `/` (homepage), `/gallery`, `/work`, `/about`. Not present on `/services`.
- **Steps to reproduce:**
  1. Enable "Reduce motion" in OS accessibility settings (Windows Settings → Accessibility → Visual effects; macOS → Accessibility → Display; or equivalent browser/OS media-feature emulation for `prefers-reduced-motion: reduce`).
  2. Load `https://aboalazm-os.vercel.app/`.
  3. Inspect computed `opacity` of elements inside `<main>` (e.g. via DevTools → Computed, or `getComputedStyle(el).opacity`).
- **Expected Result:** Scroll-triggered fade-in animations should either play normally or, when reduced motion is requested, skip straight to their final visible (`opacity: 1`) state per WCAG 2.3.3 best practice.
- **Actual Result:** Elements using the fade-in-on-scroll pattern (likely a Framer Motion `whileInView`/`initial` wrapper) get stuck at their **initial `opacity: 0` state** and never become visible. Confirmed via `getComputedStyle`, stable across repeated checks, scroll events, and multi-second waits (not a transient animation-in-progress read).
  - **Homepage:** 22 of 337 elements stuck at opacity 0 — including the status badge/coordinates, the hero subtitle paragraph, **both primary hero CTAs ("Explore the system" and "Start a commission")**, the System Constellation diagram, and **all 5 rows of the Selected Work portfolio table** (with their case-study links).
  - **Gallery (`/gallery`):** **All 52** gallery image thumbnails (`button.group` wrappers) are stuck at opacity 0 — the entire gallery is invisible.
  - **`/work`:** 9 elements affected.
  - **`/about`:** 12 elements affected.
  - **`/services`:** 0 affected (this page apparently doesn't use the same fade-in wrapper, or handles it correctly).
  - Note: this is *not* an artifact of the accessibility-tree-based checks used in an earlier lighter pass — `opacity: 0` elements still report their text content to accessibility tools and `innerText`, which is why a smoke test relying on the a11y tree or `get_page_text` alone would not catch this. It required checking real computed CSS.
- **Impact:** "Reduce motion" is a standard, common OS-level accessibility preference (motion sensitivity, vestibular disorders, or simple user preference — widely available on Windows, macOS, iOS, and Android). Any such user landing on the homepage cannot see or click the primary CTAs or portfolio links, and the Gallery page is entirely blank content-wise, even though the layout/skeleton is present.
- **Suggested Fix:** In the shared fade-in/animate-on-scroll component, add a `prefers-reduced-motion` check that sets the animated properties directly to their final state (e.g., `opacity: 1`, no transform) instead of relying on the interrupted/never-triggered animation to reach it.

## Medium Bugs

### M-1 — Theme Mode toggle in the Capabilities Live Token Playground is non-functional
- **Severity:** Medium
- **Location:** `/capabilities` → "THEME MODE" control (OBSIDIAN / ALABASTER buttons)
- **Steps to reproduce:**
  1. Go to `/capabilities`.
  2. Note the "System Card" preview panel's background color.
  3. Click "ALABASTER".
  4. Observe the button's own selected/active state updates correctly (visually marked as selected).
  5. Observe the "System Card" preview panel's background.
- **Expected Result:** Selecting ALABASTER should switch the preview card to a light theme; selecting OBSIDIAN should switch it to dark.
- **Actual Result:** The button toggle's own active-state class updates correctly, but the "System Card" preview's background color (`rgb(8, 7, 16)`, dark) **never changes** regardless of which theme is selected — confirmed by toggling back and forth with 1-second waits between each check. The other token controls in the same playground (Spacing Scale, Border Radius, Motion Duration sliders, and the Reset button) all work correctly and update the preview live.
- **Suggested Fix:** Wire the Theme Mode selection state to the actual token/CSS variable driving the System Card's background, the same way the spacing/radius/duration sliders are wired.

### M-2 — Broken live-preview iframe (insecure HTTP / mixed content) *(carried over from initial smoke test, reconfirmed)*
- **Severity:** Medium
- **Location:** `/work-ui`, middle "Live Preview" tile
- **Details:** `src="http://zad.codeandcanvas.net/"` is HTTP-only on an HTTPS page; the iframe resolves to `about:blank` (confirmed via `contentWindow.location.href`). The other two previews (same-origin HTTPS `/showcase/farm/`, `/showcase/nile-erp/`) load correctly.
- **Suggested Fix:** Serve over HTTPS, or self-host a static snapshot under `/showcase/` like the other two.

## Revised Production Readiness Score: **58 / 100**

This score supersedes the earlier smoke-test-only score of 88, which could not detect the reduced-motion opacity bug (invisible to accessibility-tree/text-based checks) or the contact-form success-state failure (required watching the network response against the UI state over time). A Critical defect in the lead-capture form and a High-severity accessibility defect hiding primary CTAs and full page sections both directly undermine the site's core business function — being a functioning showcase and conversion funnel for a design studio — and should be fixed before the site is presented as release-ready.

**Priority fix order:** C-1 (contact form) → H-1 (reduced-motion opacity) → M-1 (theme toggle) → M-2 (mixed-content iframe) → L-1..L-4.
